### Fujita Ayumi (2502515)

The module measures the edge-to-edge distance between the child’s box and each hazard box, normalises it by the child’s box height so it does not depend on camera distance or resolution, and maps it to CRITICAL, WARNING, CAUTION or SAFE zones. ## 2. AI Reflection

**Tools and framing.** The team used Claude Code (Claude Opus 5.5) and Codex (GPT-6.1 Sol Light). Claude Code supported spatial analysis, depth estimation, live-camera performance and deployment. Codex supported dataset preparation, augmentation, model-training notebooks, evaluation and documentation. We provided our approach, existing code, observed failures and professor feedback before requesting implementation. For example, we passed on the suggestion to “average the frames instead of scanning each frame” and requested a comparison against our existing best-frame selection. When responses became too complicated or changed more than intended, we narrowed requests to individual sections and specified what should remain unchanged.

**Helpful suggestions.** The AI suggested candidate depth models, and we tested MiDaS, Depth Pro and Depth Anything V2. We selected Depth Anything V2 Small based on our live-camera trials. Reducing its input size from 518 to 252 pixels made depth processing approximately six times faster. On the sample photographs checked, the reported box-depth values differed by at most 0.13. We also inspected the app’s colour depth maps to check whether nearer objects appeared brighter. These checks supported using the smaller input for our prototype, although they did not establish physical-distance accuracy.

The AI also identified a hard-coded two-thread PyTorch limit. We verified the effect through live-app measurements: processing latency was approximately 140–190 ms with two threads and 100–130 ms with four. These measurements showed a processing improvement, rather than proving the entire camera-to-alert pipeline operated at that speed.

For modelling, Codex helped organise comparisons of learning rate, input resolution, model capacity and P2 architectures. We checked the saved validation and test results rather than assuming a larger model or finer prediction grid would perform better. Experiment 3, YOLOv8s at 640 pixels, achieved the strongest detector results. The crop classifier achieved high crop-validation accuracy, but its combined pipeline increased missed hazards and false detections, so we retained the detector-only configuration.

**Amended and rejected suggestions.** For multi-frame averaging, the AI advised against averaging pixels because movement could create ghost images. It instead implemented averaging of per-frame danger scores. Our first comparison was invalid because we compared the raw overlay with the best-frame panel. After identifying the panel mismatch and retesting, we rejected averaging and retained best-frame selection to present the most concerning frame within each window. This matched our design priority, but could not recover hazards that the detector missed entirely.

Some Codex edits introduced unnecessary run controls and inconsistencies between notebook descriptions and code. We requested simpler execution, checked experiment settings and revised the markdown to match the implementation. An attempted combined Kaggle run also exceeded the session limit, so later work was separated into shorter notebooks.

**Lessons.** AI was useful for implementing ideas, locating bottlenecks and preparing tests, but required supervision when restructuring notebooks or interpreting results. We learned that high classifier accuracy does not guarantee a better detection pipeline, and faster processing does not establish better detection. In future, we would define success criteria beforehand, compare identical inputs, inspect changes before long runs and preserve working versions. AI-generated explanations would remain drafts until checked against our code, recorded outputs and observations.
